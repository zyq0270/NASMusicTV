## 1. 一句话结论

做一个**通用、可复用的半圆拨盘 Composable**（`ArcDialPicker`），以「候选列表 + 选中项 + 确认回调」为契约，采用**垂直内容流 + 中央水平选择带**模型（详见 §2.4）：手机纵向滑动手势、TV 用 D-Pad 上下键，均使内容上顶/下落、把目标项送到中央行选中，OK/点击确认。它接入两个场景——**搜索快速填写**（曲库各 tab 各给不同候选，选中即 `onFilterQueryChange` 触发已有自动搜索链路）与**播放队列快速切歌**（选中即 `resolveAndPlayByIndex`）。搜索场景的数据源是各 tab **现成的全量列表**，按**热度（快速选择次数 + 搜索次数）倒序**、同热度**按名称排序**；基础列表为空（如只连网络源、无 NAS/网盘）时用**历史统计回填**候选，基础存在时历史也并入，两类项用**不同文字风格**区分来源。播放切歌场景**不做热度排序、纯用队列原顺序**。每个可快搜类别的选择都计入热度统计（新增 `quick_pick_stats`）。设置窗口「播放统计」卡改造为「统计与快捷选择」组，纳入该数据的查看与清除。

## 2. 核心组件：半圆拨盘 `ArcDialPicker`

### 2.1 设计契约（泛型、无业务耦合）

```kotlin
// 新文件: ui/components/picker/ArcDialPicker.kt
@Composable
fun <T> ArcDialPicker(
    items: List<T>,                          // 候选项（已按热度倒序排好）
    selectedIndex: Int,                      // 当前选中索引（受控）
    onSelectedIndexChange: (Int) -> Unit,    // 滑动/D-Pad 改变选中
    onConfirm: (T) -> Unit,                  // 确认（OK / 点击 / 松手）
    onDismiss: () -> Unit,
    label: (T) -> String,                    // 展示文本（搜索场景用）
    key: (T) -> String,                      // 稳定 key
    leadingContent: (@Composable (T, Boolean) -> Unit)? = null, // 圆形封面/序号，队列场景用
    sourceOf: (T) -> PickSource = { PickSource.BASE },         // 区分基础项/历史回填项 → 决定颜色风格
    mode: ArcInteractionMode = ArcInteractionMode.AUTO,        // TOUCH / D_PAD
    title: String
)

enum class ArcInteractionMode { TOUCH, D_PAD, AUTO }
enum class PickSource { BASE, HISTORY }                        // 基础数据 / 历史统计回填（仅搜索场景用）
```

组件只负责「弧面布局 + 内容滚动交互 + 中央行选中高亮 + 确认/取消 + 按来源着色」，**不认识 Song/Album/搜索**。`sourceOf` 让业务层标注每项来自基础数据还是历史回填，组件据此套用不同文字风格（§2.2）。业务层负责备好 `items` 和回调，两个场景共用一套代码。

### 2.2 几何与视觉（半圆弧面 + 中央选择带，换成项目配色）

- **中央选择带（固定不动）**：面板垂直正中 `y = h/2` 处一条**水平**高亮带（宽约面板 80%、高约 `itemHeight`），是唯一的选择指示位。初始化 `selectedIndex = 0`，第一条内容就落在该行被选中。
- **内容项绝对位置模型（2026-11-23 定稿，⛔ 别回退）**：每项绝对槽位 `i * itemHeight`；`scrollPx` 为滚动偏移（选中第 k 项 ⇒ `scrollPx = k * itemHeight`）；屏幕相对位置 `pos = (i * itemHeight - scrollPx) / itemHeight`，`0 = 中央行`、正 = 下方、负 = 上方，`y = pos * itemHeight`。**禁止**用 `dy = (i - selectedIndex) * itemHeight - scrollAnim`——`selectedIndex` 会被扣减两次，导致选中项在屏幕上漂移。所有视觉参数（rotation / scale / alpha / 颜色 / 字号）一律基于 `pos`，随手势连续变化。
- **半圆弧面观感**：`rotation = radSign * pos * 11f`（中央水平、上下逐级倾斜），`xShift = xSign * dist² * itemHeight * 0.10f`（两端内收成弧面），`scale` / `alpha` 随 `dist = |pos|` 递减；中央行满尺寸、最高亮。`radSign` / `xSign` 由 `ArcAnchor` 决定：
  - `ArcAnchor.LEFT`（默认，播放页）：`radSign=+1, xSign=-1`——圆心在左、向右辐射，弧向右凸「)」，中央项最靠右。
  - `ArcAnchor.RIGHT`（搜索页，按钮在搜索框右侧）：`radSign=-1, xSign=+1`——圆心在右、向左辐射，弧向左凸「(」，中央项最靠左。朝向镜像由 `ArcDialPicker`/`ArcDialDialog` 的 `anchor` 参数透传，两个场景各传一次。
- 每项用 `FocusableSurface` 承载（TV 焦点环/缩放），圆形封面走 `CoverImage`（`ui/components/common/CoverImage.kt:37`），无封面显示 `♪` 或首字。
- 选中项：`NasMusicColors.Primary` 高亮 + `FontSize.title()`；非选中项 `TextSecondary` + 半透明。
- **统一配色（2026-11-23 第 7 轮定稿，⛔ 别回退）**：条目颜色只由「是否中央行」决定，与来源无关——`isCentered → NasMusicColors.Primary`，其余 `TextPrimary`，与播放页队列拨盘完全一致。
  - 演进史：初期按 `sourceOf` 区分（`BASE` 常规 / `HISTORY` 蓝 `Secondary`）→ 第二轮改深绿 `Success`（"不能用蓝色"）→ **第 7 轮直接取消来源着色**：所有者指出"既然曲库快选只列历史，就无需用深绿色了，与播放快捷切换一样的颜色"。全是历史项时，来源色不再有任何区分作用。
  - 因此 `ArcDialPicker` / `ArcDialDialog` **不再有 `sourceOf` 参数**；`PickSource` 只保留在数据层（`QuickPickCandidate.source`、`QuickPickSourceMerger` 的合并语义与单测），UI 不再消费。
  - ⛔ 不要再往组件里加按来源着色的分支，也不要恢复「历史」角标/行前图标/后缀文字（所有者："前面不要 历史 这两个字"）。

### 2.3 交互双模式

| 模式 | 触发设备 | 改变选中方式 | 确认 | 取消 |
|---|---|---|---|---|
| TOUCH | 手机竖/横屏 | `pointerInput` + `detectDragGestures`，手指**纵向滑动时内容实时跟手**：`onDrag` 每帧 `scrollPx.snapTo(dragScroll)`（本地变量累积位移避免竞态），上滑 → 内容上顶；**松手**才 `animateTo` 吸附最近项并回写 `selectedIndex`。⛔ 不在 `onDragEnd` 里一次性改 index——那样拖动过程中视觉完全不变 | 点击条目直接确认 / 松手吸附 | 返回键 |
| D_PAD | TV | 遥控器**下键** → 内容上顶 → `selectedIndex + 1`；**上键** → 内容下落 → `selectedIndex - 1`（边界可循环/钳制） | OK（遥控器 center） | 返回键 |

> 两种模式统一为「垂直内容流 + 中央选择带」模型，只是输入不同（手势纵向滑动 / D-Pad 上下键）。Windows/手机键盘 ↑↓ 复用 D_PAD 逻辑便于调试。

- 手势实现参考项目现有模式：`LibraryScreen.libraryTabSwipe`（141-172，`rememberUpdatedState` 防陈旧闭包）、`PlayerControls.kt:169-209`（tap/drag 互斥）、`VisualizerStage.kt:466-507`（方向 detector 分块）。**全仓无旋转手势组件，需自研。**
- 焦点动画用 `animateFloatAsState` 驱动角度与缩放，避免组合期副作用。

### 2.4 TV 细化设计（重点，第 5 点）

TV 没有触摸滑动，采用**垂直内容流 + 中央水平选择带**的滚轮模型（所有者 2026-11-23 定稿，替代早期「弧顶选择窗」方案）：

1. **中央水平选择带（不放弧顶）**：选择窗固定在面板**垂直正中、水平的一行**——即正常阅读的横向行，不是弧的顶点。带内项放大、高亮、显示大号文字 + 封面 + 「第 k/N 项」提示；用户只盯这一行就能判断选择。
2. **初始状态**：打开弹窗 `selectedIndex = 0`，`scrollAnim = 0`，**第一条内容即落在中央行被选中**，无需用户先移动。
3. **按键 = 内容上顶（核心交互）**：
   - 按 **D-Pad 下键** → `selectedIndex += 1`，`scrollAnim` 动画到新目标，整列内容**向上顶一格**，原第二条升到中央行被选中，第一条顶出上方淡出；
   - 再按下键 → 第三条顶上来、在中央行被选中，以此类推；
   - 按 **D-Pad 上键** → 内容**向下落一格**，回到上一条；
   - 边界：默认**循环**（首尾相接，滚轮感更强），可选钳制。
4. **一个焦点容器**：整个滚轮是一个 `FocusableSurface`（焦点环画在外框上），D-Pad 上下只改 `selectedIndex`；若每项都可聚焦，焦点会在弧面项间乱跳、且非中央项难辨识。**单一焦点容器 + 内容滚动**更稳。
5. **数字键快捷**：TV 遥控器数字 1–9 直接跳到前 9 项（可选，P2）；这是「快速」体验的关键补充。
6. **可视项数收敛**：中央行上方、下方各显示 **2–3 项**（总计 5–7 项，`spanCount`），再远的项淡出裁掉；过多会导致边缘文字压缩不可读。候选项多时靠滚动翻页，不全部铺开。
7. **首焦与返回**：弹窗打开时焦点自动落到滚轮容器；返回键弹窗内用 `BackHandler`（真 Dialog 是独立窗口，Activity dispatcher 收不到按键，见 `DialogBackHandler.kt:54-57`）。
8. **性能**：TV 上滚动动画只更新一个 `Animatable` float（`scrollAnim`），`Canvas` 重绘弧线 + 若干 item 的 `graphicsLayer` 平移/缩放；不要每帧重组整棵列表。

> 结论：**同一组件、两种交互模式**，TV 不是「退化的手势版」，而是把连续滑动改为「D-Pad 上下键 → 内容上顶/下落 → 中央水平行选中」，与手机纵向滑动手势一致，体验更可控。

## 3. 场景 A：搜索快速填写（第 2 点）

### 3.1 入口改造（搜索框右边加小按钮）

- `SearchField`（`CommonComponents.kt:66-112`）是胶囊按钮，点击弹 `TextInputDialog`。**不改它本身**，而是在调用点的 `Row` 里，搜索框右侧加一个小 `FocusableSurface` 图标按钮（图标建议 `Icons.Default.RadioButtonUnchecked` 或自绘弧线图标）。
- 曲库搜索框在 `LibraryScreen.kt:566-574` 定义 `searchField`，渲染两处：
  - 竖屏（`:627`）搜索框独占整行 → 在其 `Row` 内右侧加按钮；
  - TV/横屏（`:640-649`）搜索框 `Modifier.width(240.dp)` 与 `playAllChip()` 同排 → 在搜索框后、`playAllChip` 前插入按钮。
- `LibraryScreen` 新增参数 `onOpenQuickPick: () -> Unit`，弹窗开关状态 `showQuickPick` 放 `LibraryScreen` 内部（与现有 `showSearchDialog` 同级），**Branch 只接线不改状态归属**。

### 3.2 各 tab 候选内容映射（第 2 点「内容与 tab 一致」）

`LibraryTab` 共 8 个（`LibraryScreen.kt:88-97`）。**候选池只取历史查询记录，不取当前页面的列表数据**（2026-11-23 第三轮定稿，见 §3.2.1）：每个 tab 一个统计桶（`category = LibraryTab.name`），拨盘列出的就是该桶里的历史值，按热度倒序。

| LibraryTab | 候选内容 | 数据源（只列历史） | 填入搜索框的值 |
|---|---|---|---|
| ALBUMS | 曾搜索/选中的专辑名 | `quick_pick_stats["ALBUMS"]` | 值本身（String） |
| ARTISTS | 曾搜索/选中的艺术家名 | `quick_pick_stats["ARTISTS"]` | 值本身 |
| SONGS | 曾搜索/选中的歌曲名 | `quick_pick_stats["SONGS"]` | 值本身 |
| GENRES | 曾搜索/选中的流派名 | `quick_pick_stats["GENRES"]` | 值本身 |
| YEARS | 曾搜索/选中的年代 | `quick_pick_stats["YEARS"]` | 值本身 |
| SEARCH | 高频搜索词 | `quick_pick_stats["SEARCH"]` ∪ `search_history`（归一化去重取 max count） | 值本身 |
| DISCOVER | 曾搜索/选中的发现页歌曲名 | `quick_pick_stats["DISCOVER"]` | 值本身 |
| RADIO | 曾搜索/选中的电台名 | `quick_pick_stats["RADIO"]` | 值本身 |

> 候选与搜索维度无关的一点是：`SearchViewModel.searchSongsOnServer` 会按当前 tab 选 `SearchType`（ALBUMS→ALBUM、ARTISTS→ARTIST、其它→SONG_NAME_OR_ARTIST，`:254-259`）。填入的**值本身带类型语义**（专辑名/歌手名），与 tab 一致即可正确搜索。
> ⚠️ 历史记录天然稀疏（冷启动为空），因此拨盘在无历史时显示空态而非回退到页面列表——这是所有者的明确要求（"不列出当前页面的数据"）。

> 候选池与搜索维度无关的一点是：`SearchViewModel.searchSongsOnServer` 会按当前 tab 选 `SearchType`（ALBUMS→ALBUM、ARTISTS→ARTIST、其它→SONG_NAME_OR_ARTIST，`:254-259`）。填入的**值本身带类型语义**（专辑名/歌手名），与 tab 一致即可正确搜索。

### 3.2.1 候选源：只列历史查询记录（2026-11-23 第三轮定稿，⛔ 别回退）

**定稿口径**：所有 tab 的快选窗**只列该类别的历史查询记录**，不列当前页面的列表数据（不列专辑列表、不列艺术家列表、不列当前搜到的歌曲）。基础列表一律传 `emptyList`，因此候选的 `sourceOf` 全部是 `HISTORY`，全部走深绿文字。

历史版本（已被否决，⛔ 不要照抄）：「基础数据 + 历史回填」的两段式合成——列出页面全量列表、历史只作为补充。被否决的实机表现：① 搜出歌曲后弹窗里历史项与新搜到的歌曲名混在一起，用户分不清；② 无数据页面里历史项未变绿（旧代码里 `base` 非空时把同名的历史项降级成 `BASE`）；③ 其他页面列出当前页面数据而非历史，与"快速回填历史查询"的产品语义不符。

**合成规则**（每个 tab 打开拨盘时执行，纯函数 `QuickPickSourceMerger.merge` + `QuickPickRanker.rank`）：

```
该 tab 最终候选 = merge(emptyList<String>(), 该类别历史数据)
  1. 基础列表传空 ⇒ 没有任何 BASE 项，全部标 sourceOf = HISTORY（深绿）；
  2. 历史数据：general tab 取 quick_pick_stats[category] 的 value；
     SEARCH tab 额外并入 search_history 的词，按 ArtistSplitter.normalizeKey 归一化分组、
     每组取 count 最大的那条（同一关键词在两个桶里各有一份 count，取 max 而非相加，避免重复计数）；
  3. 去重：以归一化 key 为准，同名只留一条；
  4. 排序：QuickPickRanker.rank 按该类别的 count 倒序，同热度按名称自然序，limit = 7；
  5. 无历史 ⇒ 空候选，拨盘显示空态（不回退页面列表）。
```

- **热度唯一口径**：热度 = 该 tab 自己桶里的 `count`（`quick_pick_stats[category].count`）。⛔ 不再混入全局 `search_history` 的次数，否则跨类别污染（在 SONGS 里搜过的词会抬高 ALBUMS 的热度）。
- **写入点（两个都必写，漏一个就会"热度不涨"）**：
  1. 拨盘 `onConfirm` → `onRecordQuickPick(category, value)`；
  2. 手动搜索确认 → `TextInputDialog` 的 `onConfirm` 与 `onHistorySelect` 里 `if (query.isNotBlank()) onRecordQuickPick(activeTab.quickPickCategory(), query.trim())`。
- **离线可用**：`quick_pick_stats` 在本地 DataStore，不依赖任何后端连接。

## 5. 数据统计存储的定义及内容（第 3 点前半）

### 5.1 定位：与现有统计的分工

| 存储 | 键 / 内容 | 维度 | 用途 |
|---|---|---|---|
| `search_history`（现有） | `List<SearchHistoryItem(query,lastSearchedAt,count)`，`AppPreferences.kt:659` | 扁平、无 tab、30 天 TTL / 200 条 | 「最近/热门搜索」chip（搜索框内）；⛔ **不再作为 tab 热度来源**（2026-11-23 修正，见 §5.4） |
| `play_counts` / `play_stats_*`（现有） | 歌曲播放次数、月/日计数 | 歌曲、时间 | 播放统计页 |
| **`quick_pick_stats`（新增）** | `List<QuickPickStat(category,value,count,lastPickedAt)` | **类别（tab）+ 内容值** | **搜索拨盘候选排序（热度倒序）**、设置页统计 |

> 三者分工：播放统计记「播过什么」；**搜索热度只由 `quick_pick_stats` 构成**（按类别分桶，写入点含拨盘选中与手动搜索确认）；搜索历史只服务「最近/热门搜索」chip，不参与 tab 热度。
>
> **覆盖全部可快搜类别（第 2 点）**：所有接入拨盘的类别（ALBUMS/ARTISTS/SONGS/GENRES/YEARS/SEARCH/DISCOVER/RADIO 及 P2 扩展的电台/网盘等）选中时统一走 `recordQuickPick(category, value)`，按 `category` 分桶累计。任何 tab 都不例外，保证「各类数据都有热度统计」。播放切歌（QUEUE）**不写此统计**。
>
> ⚠️ **"有统计"≠"能弹窗"**：拨盘只列历史，桶为空就弹不出来。因此每个类别都必须有一条**不依赖拨盘**的写入路径，全景与审计见 §5.3.1（2026-11-23 第 7 轮补了流派/年代/电台三处）。

#### 5.3.1 各类统计的写入点全景（2026-11-23 第 7 轮审计）

拨盘是唯一的"快选"入口，所以**桶为空 ⇒ 按钮没内容 ⇒ 弹不出来**。每个类别必须至少有一条**不依赖拨盘**的自然写入路径。审计结果（改前 → 改后）：

| 类别 | 改前写入点 | 改前能不能弹出来 | 改后写入点 |
|---|---|---|---|
| SEARCH | 搜索框确认 / 选历史词 / 拨盘选中；另并入 `search_history` 词 | 能（`search_history` 兜底） | 不变 |
| ALBUMS | 停在 ALBUMS tab 用顶部搜索框确认 / 拨盘选中 | 能，但要在该 tab 手动搜过字 | 不变 |
| ARTISTS | 同上 | 同上 | 不变 |
| SONGS | 同上 | 同上 | 不变 |
| GENRES | 只有顶部搜索框确认，且**确认后强制跳 SEARCH tab** | 基本不能——点流派卡片才是唯一自然操作，它不写统计 | **＋点流派卡片**（`onSongsByGenre` 包装后先 `recordQuickPick` 再调原回调） |
| YEARS | 同上 | 同上 | **＋点年代卡片**（`onSongsByYear` 包装） |
| RADIO | **无**——电台 tab 用自己的搜索框（`RadioTab.onSearch`），不走顶部共享 `searchField` 的确认回调 | **永远不能**（结构性缺陷，不是数据稀疏） | **＋电台搜索框确认**（`onSearch` 包装） |
| DISCOVER | 停在 DISCOVER tab 用顶部搜索框确认 | 勉强能（发现页习惯用维度筛选，很少打字） | **＋点歌曲播放**（`DiscoverTab.onPlaySong` 包装；所有者第 8 轮裁定「点歌曲就计入」） |
| QUEUE（播放页切歌） | 无，按设计不写 | 不适用（列的是队列本身，不需要热统计） | 不变 |

- **判据：什么算"一次查询"** → 会产生「按某值去取内容」的动作。点流派/年代卡片 = `onSongsByGenre`/`onSongsByYear` 去取该流派/年代的歌单，**是**查询；点电台 = 直接播放，**不是**查询。
- **例外（所有者裁定）**：`DISCOVER` 点歌曲播放**也计入**（第 8 轮）——发现页本身没有文本搜索习惯，不加这条则该桶永远为空；且该桶语义就是「发现页里挑出来听过的歌」，与"播放历史副本"并不冲突（后者是全量 `play_counts`）。其余 tab 的播放仍不计入，避免快选窗被随手听过的歌占满。
- **冷启动兜底（门禁 G8）**：bucket 为空时点按钮**不再静默关闭**，而是直接打开搜索输入框——这次键盘搜一次即写入本 tab 桶，下次点按钮就有快选内容。这样 8 个类别的按钮在任何时候都有响应，不会出现"点了没反应"。
- ⛔ 别再"用当前页面列表兜底"：所有者明确要求只列历史（§3.2.1）。

### 5.4 排序聚合器（纯函数，可单测）

```kotlin
// 新文件: data/stats/QuickPickRanker.kt
object QuickPickRanker {
    fun <T> rank(
        candidates: List<T>,             // 合成后的候选（现已全部来自历史统计，见 §3.2.1）
        valueOf: (T) -> String,          // 候选项的名称（用于热度匹配与同分排序）
        pickStats: List<QuickPickStat>,  // 当前类别的快选统计
        searchCounts: Map<String, Int> = emptyMap(),  // 搜索历史按词聚合的 count
        limit: Int = 7                   // TV 弧上可视项数
    ): List<T>
    // 热度 heat(value) = pickStats[value].count + searchCounts[value]
    // 排序：① heat 降序 ② heat 相同按名称 valueOf 的自然序（大小写不敏感）升序
    // 无热度的候选项 heat=0，按名称排序排在热项之后
    // 取前 limit 项；候选项少于 limit 时全部返回
}
```

排序规则（对应第 1 点）：
- **主序**：热度 = 该类别（tab）的 `quick_pick_stats[value].count`，倒序（最热最常排在列表前部，初始即落在中央选择行）。
  > **2026-11-23 修正（所有者质疑后定稿）**：⛔ 不再把全局 `search_history` 的次数加进热度。原口径 heat = 快选次数 + 全局搜索次数有三处错误：① `search_history` 不区分 tab，ALBUMS/ARTISTS/GENRES 等 tab 会被无关的全局搜索词污染；② 一次拨盘选择会同时写 `quick_pick_stats(+1)` 与 `search_history(+1)`，相加等于**一次操作算两次**；③ 用户手动在搜索框搜索时并不写 `quick_pick_stats`，导致统计与实际使用对不上。
  > **修正后口径**：`quick_pick_stats[category]` 是唯一热度来源，写入点覆盖「拨盘选中」与「手动搜索确认（含选历史词）」两条路径，二者都按当前 tab 分桶。`QuickPickRanker.rank` 的 `searchCounts` 参数保留但调用方不再传（默认空），历史遗留的 `search_history` 仍只服务「最近/热门搜索」chip。
- **次序（同分）**：按**名称内部排序**——`valueOf` 自然序升序（大小写不敏感，中文按 `String` 的 Unicode/拼音由 `Locale` 决定，实现时用 `Comparator` 明确，保证单测可复现）；
- 冷启动（无统计）时所有项 heat=0，退化为纯名称排序，弧上仍有内容。
- **本节只用于搜索场景**；播放切歌不调用本聚合器（见 §4.3）。

- 每个 tab 打开拨盘时，`buildQuickPickCandidates(tab, historyItems, stats)` 取该 tab 桶（SEARCH 再并 `search_history`）→ `QuickPickSourceMerger.merge(emptyList, stats)` → `QuickPickRanker.rank` → 喂给 `ArcDialPicker.items`。
- 这就是「**按热度倒序、同分按名称**」的落点。
