# 我把开源软件放在 GitHub，为什么没登录的人打不开？——一次「登录态幻觉」排查实录

> 写在前面：我维护着一个开源 TV 音乐播放器 NASMusicTV。最近陆续有人反馈"你的仓库打不开""Release 里没有安装包"。可我自己点开一切正常——因为我一直登录着 GitHub。这篇文章记录我是怎么把这件事查清楚的：它既不是仓库权限设错，也不全是 GitHub 故障，而是「登录态差异 + 压根没发 Release + 匿名请求故障」三层原因叠在一起。现在项目已经迁到 Gitee，并有了独立产品主页，文末给出链接。顺带聊聊项目最近的版本进展。数据截至 2026 年 11 月 16 日。

## 一、现象：我觉得没问题，用户说打不开

收到的反馈大致两类：

- "你 GitHub 仓库我打不开 / 转半天白屏。"
- "Release 页面是空的，没地方下 APK。"

而我的视角是：仓库点开秒开、Release 页面……好像确实我也没仔细看过，一直是从 README 里的产品主页链接发安装包。

这里有个特别容易掉进去的坑：**作者本人永远是登录态**。GitHub 对登录用户和匿名用户走的是两套请求路径、两套限流策略。你不退出登录、不用无痕窗口复现，就永远看不到普通访客看到的世界。这是排查这类问题的第一步，也是我这次最大的收获。

## 二、第一层：仓库本身其实没权限问题

先排除最朴素的猜测——是不是仓库设成私有、或者对未登录用户隐藏了？

用 GitHub API 不带任何身份查了一下：

```
visibility  : public
private     : false
```

仓库是公开的，匿名可读，**权限层面没问题**。所以"打不开"不是仓库被设成了私有。

但同一个查询里还藏着一条关键信息：

```
has_downloads : false
releases      : []   ← 空的
```

**这个仓库从头到尾没有发布过任何一个正式 Release。** 于是第二类反馈的答案直接落地了：用户去 `/releases` 找安装包，当然是空的——因为那里什么都没有。我平时发包走的是 README 里的产品主页（maozi.io 部署地址）和本地文件，GitHub Release 这个"开源项目默认的下载入口"一直是荒着的。

> 一句吐槽：对国内用户来说，GitHub Release 本来就是够不稳定的下载源；我却连这个入口都没填，等于把"找不到安装包"这件事亲手做实了。

## 三、第二层：11 月那几次故障，专挑"未登录用户"下手

那"仓库打不开"呢？这就要说到 11 月 GitHub 官方那一串故障了。我把官方状态页的记录摘出来（时间为 UTC，来自 githubstatus.com）：

| 日期 | 影响 | 官方原话里的关键限定 |
|---|---|---|
| 11/8 | 未认证用户大量超时、API Requests 降级，约 2 小时 | "部分**未认证用户**超时" |
| 11/9 | 匿名用户大量 504，release 下载、走匿名调用的 CI 任务失败，约 3 小时 | "**登录用户与带认证的请求不受影响**" |
| 11/11 | Actions / Pages / Copilot / Webhooks 多产品降级，官方标注 Major，33 分钟 | 影响面更广，但依旧是短暂降级 |

看到 11/9 那条我就明白了——**官方自己写明"登录用户不受影响"**。这几乎就是为我这种场景量身定做的：作者登录着，测一万遍都正常；访客没登录，正好撞在匿名请求 504 上，于是"你的仓库打不开"。

截至 11/16，官方状态页显示 11 个组件全部正常（All Systems Operational），这次故障已经过去。但它暴露的问题不会自动消失：**我的项目可访问性，绑在了一个我控制不了、且会针对匿名流量抖动的平台上。**

## 四、第三层：国内网络链路，让体感再打一次折

即便 GitHub 官方全绿，国内访问 github.com 还有一层老问题：跨境链路拥塞、DNS 解析到不理想节点、代理规则没生效。这一层加上前面两层，就是用户体感的"打不开"——三种原因长得一模一样，都是白屏或 504，用户不可能替你区分。

（顺带一提，我这台机器今天裸连 github.com 直接 `schannel: server closed abruptly`，20 秒超时；得走本机 DevSidecar 代理 `127.0.0.1:31181` 才能通。这本身就是链路层的活例子。）

## 五、怎么自查：别再用你自己的登录态测了

给同样把项目放 GitHub 的朋友一套可复现的自查清单：

1. **用无痕窗口 / 退出登录访问**：`github.com/<你>/<仓库>` 和 `/releases` 各看一遍。这才是访客视角。
2. **查仓库是不是 public**：`gh api repos/<owner>/<repo> --jq '.visibility, .private'`。
3. **查有没有 Release**：`gh api repos/<owner>/<repo>/releases`。空数组就说明你根本没发——用户自然找不到下载。
4. **看官方状态页** `githubstatus.com`：全绿 → 多半是链路或配置问题；有黄有红 → 对号入座看影响组件，尤其注意"unauthenticated users"这类措辞。
5. **分层排除链路**：换网络（手机热点）、换 DNS、`ping` / `nslookup` 看丢包和解析；终端报 443 超时就核对 `git config --global http.proxy` 是不是留了失效地址。
6. **核对登录态差异**：无痕 504、登录后正常 → 基本就是 GitHub 匿名流量那类故障，等官方修复即可，不用改自己的代码。

一句话原则：**先分清是"没发 Release""官方匿名故障"还是"本机链路"，再决定是补内容、是等、还是换渠道。**

## 六、给开源作者的三个教训

1. **Release 是开源项目的门面，别空着。** 哪怕先传一个源码包，也比 `/releases` 一片空白强。用户找安装包的第一站就是那里。
2. **下载入口别押在单一平台。** GitHub Release + 自建产品主页直链 + 可信镜像，多给几条路。GitHub 抖一下，用户还有地方可去。
3. **用访客视角验收。** 每次发版，拿无痕窗口把仓库页、Release 页、下载链接走一遍。作者的登录态是最会骗人的测试环境。

## 七、我的应对：迁移到 Gitee，另起一个产品主页

上面这些教训，我不是只写写而已——项目现在已经有了两个 GitHub 之外的入口，我用无登录视角都验证过是公开可达的：

- **Gitee 仓库（已迁移）**：https://gitee.com/hxzhang2000/NASMusicTV
  公开可访问，README 完整搬运（中文版），功能特性、界面预览、下载安装、构建说明一应俱全。国内用户不用再跟 github.com 的跨境链路较劲。
- **产品主页**：https://zd7gxll02-nasmusictv-10j3m3sd.maozi.io/
  一个独立的展示与下载站，公开可访问。首页直接给出「5 种 NAS 后端 / 4 路并行音源 / 27 个可视化效果 / 70 种照片墙转场」的概览，还有 What's new、下载页（`/download`）、效果库（`/effects`）、截图页（`/screens`）等分栏目，v2.39.18 的更新摘要也在上面。对用户来说，这是比 GitHub Releases 直观得多的入口。

这样一来，访客的路径就变成了：产品主页看介绍和下载 → Gitee 看源码 → GitHub 只作为上游备份。GitHub 再抖，也不会把用户堵在门外。

Gitee 仓库 README 里的「下载地址」也已经换成了百度网盘分享链接，国内用户取安装包不必再走 GitHub Releases——从源码入口到下载入口，这条迁移算是走完了最后一公里。

## 八、软件新进展：NASMusicTV 最近做了什么

说完访问问题，聊聊项目本身。当前版本 **v2.39.18（versionCode 203）**，主线是电视实测驱动的连续修复：

- **FLAC 在老电视上整进程崩溃** → 无损档自动降级为 320kbps，弹一次 Toast 说明原因后跳过该曲。
- **逐行歌词不跳行**（`derivedStateOf` 捕获普通参数导致派生值永不重算）、**8 个页面在电视上的顶部留白**、**设置页长值被压成三行**等交互问题逐一收口。
- **日志里两类 E 级"假错误"**：照片解码取消本是预期行为、IP 定位免费接口在国内常年不可达，之前都刷成红色报错，把真正的错误挤没了（日志窗口只有约 2 分钟）——现已分别降级并加兜底。
- **照片墙大改**：新增 33 种转场，总数一度做到 76 种；随后主动下线 6 个"拼块拼不回原图"的效果，回退到 70 种。另加了拍摄日期水印，并修好 NAS「家庭视频和照片」库扫不到照片的根因（相册级回退，实测读到 2 万张）。
- **新增频谱效果「街机合集」**：内嵌魂斗罗，自动 bot 驱动、8 关可循环通关，图形素材用上游真图打成 1024×1024 图集（489 帧、约 56 KB）。
- **两轮全库代码审查落地**：11/9 处理 154 项发现（含一个 API<26 上 `clipPath` 打崩渲染进程的 Critical），11/13 归档的 59 条终稿发现在 v2.39.18 内整改完。
- **GitHub 反馈闭环**：统一正式签名（v2.38.3 起终于不用每次更新都卸载）、遥控器焦点被背景盖住、飞牛曲库返回 0 首（逐条容错解析）、高质量人声分离在 32 位 / 内存不足电视上直接失败（v2.39.5 加内存预检，不足 700MB 立即提示并回退快速模式）。目前仍有 2 个 issue 开着：K 歌麦克风采集与混音、安卓 4.x 遥控器焦点丢失。

产品主页上还有更细的版本摘要和 17 张真机截图，想直接看效果的可以去逛逛。

## 九、结尾

这次排查最扎心的地方不是 GitHub 抖了几次，而是我作为作者，居然一直用登录态去判断"用户能不能访问"。开源不是把代码 push 上去就结束——**让别人真的拿得到，是另一半工作**。

镜像已经加上了，Release 也该补了。GitHub 抖不抖，从今天起不再是用户能不能用上这个软件的决定因素。版本会继续发，但"用访客视角验收"这条，我会记很久。
