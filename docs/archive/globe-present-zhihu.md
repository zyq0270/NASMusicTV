# 我用单个 HTML 文件做了一颗「活着的」生态地球，这里把踩过的坑都摊开讲

> 源文件：`globe-present.html`（约 3655 行，纯前端，零后端、零构建；与本文同目录归档）
> 技术栈：Three.js r160 + 原生 WebGL + Canvas 2D，模型来自 Quaternius / Poly Pizza（CC0 / CC-BY）

这篇文章不讲"如何用 three.js 画一个球"——网上教程很多。我想讲的是把一个**程序化生成的卡通地球**做到"看起来有生命"的过程中，那些**教程里不会写、只有真机跑起来才会撞上的坑**，以及每个坑我当时是怎么定位、怎么取舍的。

最终效果：一颗自动旋转的地球，海陆、云层、昼夜晨昏线、四季色调、山峦积雪全部程序化生成；15 种动物 19 只 + 150 棵树散布在全球陆地上，有的沿地表行走、有的成片成林，间歇性还有龙卷风扫过海面和陆地。整页没有一行后端代码。

---

## 一、总览：它到底由几层构成

整个画面不是"一个模型"，而是**十几层透明球壳 + Sprite + 2D 画布叠出来的**，按渲染顺序从里到外大致是：

| 层 | 半径 | 作用 |
|---|---|---|
| 地球本体 | 1.0000 | MeshStandardMaterial，颜色 + 凹凸 + 粗糙度三张程序化贴图 |
| 陆地季节色层 | 1.0012 | ShaderMaterial，秋季草地泛黄、冬季整块大陆盖雪 |
| 山脉壳 | 1.0000 起，径向抬起 | 独立 256×128 球壳，顶点沿法线方向抬起形成山体 |
| 夜面压暗 / 晨昏霞光 | 1.0025 | 半透明冷蓝压暗夜半球，晨昏带透暖橙 |
| 城市灯火 | 1.003 | AdditiveBlending，夜面撒 6500 个暖色灯点（当前版本按需求关掉） |
| 海面流动高光 | 1.004 | Additive，只在昼面海上出镜面 + 滚动波纹 |
| 云影 | 1.002 | 把云纹当 alpha，在地表投很淡的暗斑 |
| 双层云 | 1.070 / 1.095 | 反向慢速旋转，形成视差 |
| 大气光晕 | Sprite | 面向相机的径向渐变，**不是几何球**（后面细说为什么） |

再往外，太阳 / 月亮 / 极光 / 流星 / 鸟群 / 星空各归其位。理解这个"洋葱结构"是看懂整个文件的前提——**地球上任何一个视觉现象，本质都是往某个半径上再套一层壳**。

## 二、地形：用噪声造一个可信的星球

地球不依赖任何卫星贴图，全靠 `fbm3`（分形布朗运动）在 GPU 之外的 CPU 上逐像素算出来：

```js
function elevationP(p) {
  var e1 = fbm3(p[0]*1.6+0.37, p[1]*1.6+0.11, p[2]*1.6+0.53, 5);
  var e2 = fbm3(p[0]*4.3+1.2,  p[1]*4.3+2.4,  p[2]*4.3+3.7,  4);
  var e3 = fbm3(p[0]*9.0+0.6,  p[1]*9.0+3.1,  p[2]*9.0+5.2,  3);
  return clamp01(0.46 + e1*0.34 + e2*0.12 + e3*0.08);
}
```

三个倍频（大陆轮廓 / 中尺度 / 细节）叠加，`0.46` 是海平面阈值。一次循环里我同时算出四样东西：

- **颜色图**：深海→浅海→沙滩→草地→森林→岩石→雪帽，按高程分带
- **凹凸图（bumpMap）**：海面平坦、陆地按高度 + 细节噪声起伏
- **粗糙度图（roughnessMap）**：海面略光滑出高光、陆地哑光
- **类别网格 `clsGrid`**：0 海 / 1 沙 / 2 草 / 3 林 / 4 岩 / 5 雪 / 6 高草

**关键设计**：这次循环顺手把每个像素的高程 `e` 存进了 `ELEV.data`。后面所有需要判断"这点是不是陆地"的逻辑（动物落点、森林撒点、龙卷风路径、城市灯火），全部改成查这张表 + 双线性插值，**不再重跑噪声**。

这是个典型的性能转折点：`elevation()` 原本是纯 CPU 热点，每帧被调用几百次，每次都要跑 5+4+3 个噪声八度。改成查表后**零额外噪声计算**，而且类别网格还顺带喂给了城市灯火、海面掩膜、季节色层——一份计算，多处复用。

## 三、贴地：平底模型站在球面上为什么会悬空

这是最反直觉的一个坑。动物和树的底面是平的，但球面是弯的——模型中心相切于球面时，**四条边的脚下其实悬空了**，悬空量是 `a²/2R`（`a` 为模型半宽）。

真实比例下一只鹿只有地球半径的千万分之一，悬空量小到看不见。但我刻意**不按真实比例**渲染（那样屏幕上连 1px 都不到），模型统一放到屏幕 40~60px 高，悬空就变得肉眼可见了。

解法是按每个模型**缩放后的实际半宽**算球面凹陷量，主动下沉：

```js
function groundRadius(size, s) {
  var a = Math.max(size.x, size.z) * s * 0.5;      // 缩放后半宽
  var sag = R - Math.sqrt(Math.max(0, R*R - a*a)); // 球面凹陷量
  return R - sag*0.6 - 0.0015;                     // 下沉 sag 的 60% 切平
}
```

下沉 `sag*0.6` 而不是 `sag`，是为了既吃掉边缘空隙、又不至于把脚陷进地表。这一版起，行走动画里也**不再叠加上下起伏（bob）**，脚底始终贴地。

## 四、行走：骨骼动画 vs 程序化步态

动物能不能走，取决于 GLB 里有没有骨骼动画。这里分成三类，处理方式完全不同：

**① 有骨骼 Walk 剪辑的**（鹿、兔 + Quaternius 12 种动物）：直接 `AnimationMixer` 播放。但这里有个新手必踩的坑——

> ⚠️ 普通 `clone(true)` 不会重建 `skeleton.bones` 引用，多实例会**共用同一套骨架、动画串台**。必须用 `SkeletonUtils.clone`。

**② 完全没有骨骼的**（长颈鹿、熊猫：GLB 只有"1 节点 + 1 mesh、0 骨骼"）：程序化补两套动作——

- 在 `gait` 容器上挂一个 `AnimationClip`，做摇摆 / 点头 / 前后微摆；
- 给网格加两个 morph target，按顶点高度加权（只动下半身）、按 x/z 象限分组，让**对角腿交替**摆动。

morph target 这里藏着一个极隐蔽的 bug，单独拎出来讲：

**③ 树**：固定不动，只有微摆。

### morph target 的「周期性长大缩小」

现象：模型每隔几秒会周期性地"膨胀再缩小"一圈。

根因链条：`SkeletonUtils.clone` 不保证复制 `mesh.morphTargetsRelative` 这个标志。一旦它为 `false`，shader 按 `(morphTarget - position) * influence` 计算——如果我只在 morph target 里存**位移量（delta）**，近零的 delta 会把顶点拉向原点，模型就周期性塌向中心。

修法：morph target 必须**存绝对位置 = 原始顶点 + 位移**，而不是只存 delta：

```js
A[i*3] = x + dx; A[i*3+1] = y; A[i*3+2] = z + dz;  // 绝对位置
```

同一类"顶点被拉向原点"的坑，在另一处（花朵昼夜变暗）也踩过一次，根因都是**误以为 BufferAttribute 是引用，实际是复制**——这个后面第五节再说。

### 长颈鹿横着走

`orient_probe.html` 实测发现：长颈鹿头顶顶点 100% 落在局部 **+X**，而其它所有物种都在 **+Z**。行走系统的约定是"局部 +Z 为前进方向"，于是长颈鹿整只横着走。

修法：给 MODELS 加 `facing: -Math.PI/2`，摆放时右乘一个绕局部 Y 的旋转，把 +X 摆到前进轴。

> 这个坑的教训是：**不要假设美术资源的朝向约定统一**。不同来源的 GLB，前进轴可能是 +X、+Z、甚至 -Z，落库前必须逐个探测。

## 五、程序化动画里两个「看不见的杀手」

这两处都没有报错，纯靠肉眼 + 断点才能抓到，写在这里希望别人少走弯路。

### 杀手一：`Float32BufferAttribute` 是复制，不是引用

我想让花朵在夜面变暗。`PointsMaterial` 不吃场景灯光，所以只能自己算昼夜系数再压暗顶点色。第一版我这样写：

```js
var arr = fGeo.attributes.color.array;  // 以为拿到的是引用
arr[i] = darkened;                       // 改它
```

**没用。** 表现是"花朵昼夜不变暗"。因为 `Float32BufferAttribute` 内部是 `new Float32Array(array)`——**它复制了一份**，我改的是局部副本，GPU 那边纹丝不动。

正确做法是反查真正的 array 写进去，并手动标记上传：

```js
fGeo.attributes.color.array[i] = darkened;
fGeo.attributes.color.needsUpdate = true;
```

同一个根因还引发了"雪花不飘落""落叶不飘落"——三处一起中招。

### 杀手二：`cross()` 返回普通数组，没有 `.normalize()`

秋季落叶想加一点横向漂移，需要算切面方向。我用了自写的 `cross(a, b)`——它返回的是**普通 JS 数组**，不是 `THREE.Vector3`。于是每帧抛：

```
tang.normalize is not a function
```

修法是手动除以模长：

```js
var tlen = Math.sqrt(tang[0]*tang[0] + tang[1]*tang[1] + tang[2]*tang[2]);
if (tlen > 1e-9) { tang[0] /= tlen; tang[1] /= tlen; tang[2] /= tlen; }
```

> 这类 bug 的共性：**自写的向量工具函数和 three.js 原生 Vector3 长得太像**，调用时脑子里默认它有全套方法。要么统一返回 Vector3，要么把自写函数命名区分开。

## 六、四季：最难的不是换色，是「换色的时序」

四季系统我返工了四五轮，每一轮都是用户实测反馈驱动的。这里挑三个最有代表性的。

### 6.1 `?season=3` 加了冬天却不下雪

调试参数 `?season=N` 想钉死在某一季，结果冬天一片绿，雪花积雪全没有。

根因：季节"出现强度"我用的是 `sin(π*(sf-季号))`，而 **`sin` 在季号边界恰好为 0**——所以 `season=3` 一进来，冬季强度就是 0，永远看不见。

修法：改成和色调同一套线性插值，钉档 `season=N` 就是**纯净的第 N 季**。

### 6.2 材质名是复数，正则全部落空

树冠要换色，得先把树叶材质从树皮里挑出来。我用 `/leaf/` 去匹配，结果**一个都识别不到**，10 个材质全被当成树干。

原因哭笑不得：材质名是复数 **`NormalTree_Leaves`**——`Leaves` 里并不包含子串 `Leaf`（`L-e-a-v` ≠ `L-e-a-f`）。正则改成同时接受 `leaf|leav|foliage|canopy` 才解决。

### 6.3 乘法染色永远染不出冷蓝灰

冬天树冠想变成冷蓝灰、秋天变正红，但绿叶贴图**乘任何系数都还是绿的**——绿通道永远压不下去。

根因：`color *= tint` 是乘法染色，只能在原色基础上缩放，无法改变色相。

修法：改用 `onBeforeCompile` 注入 shader——**取贴图亮度当明暗、季节色当色相，二者相乘**：

```glsl
float lum = dot(diffuseColor.rgb, vec3(0.2126, 0.7152, 0.0722));
float k = clamp(lum / max(0.05, uLeafLum), 0.30, 2.6);
diffuseColor.rgb = mix(diffuseColor.rgb, uLeafTint * k, uLeafMix);
```

这里还有个配套坑：树皮和树叶的 `defines` 完全相同 ⇒ three.js 的程序缓存键相同 ⇒ **树皮会复用树叶的着色器而被一起换色**。必须给叶子材质单独设 `customProgramCacheKey`。

### 6.4 积雪「突变」与合成顺序

用户反馈：秋冬交界积雪**突然**出现、冬春交界**突然**消失。

第一层根因：早期用 `alphaMap + alphaTest:0.5`，`alphaTest` 是硬阈值，阈值处整块大陆瞬间出现/消失。

第二层根因（更隐蔽）：即便改成连续渐变，如果用"**二选一**"逻辑（`snowA > a` 就换成雪），草地黄的 alpha 会先掉、透出下面的绿 ⇒ 看起来"**黄跳变成绿，再逐渐变白**"，顺序反了。

正确做法是 **over 合成**：底层草地色随季节连续插值（秋黄→冬绿），上层雪连续插值，用白色**连续盖住**底色：

```glsl
float gA = grassA * (1.0 - sc);        // 草地按被覆盖比例残留
float w   = gA + sc;
col = (gCol*gA + sCol*sc) / max(w, 1e-4);
a   = w;
```

于是：秋冬交界**黄→连续变白**（底下黄变绿的过程被雪盖住看不见）；冬春交界**白→连续显绿**。全程无跳变。

同时草地的"变绿"我干脆**不插值颜色**——底色恒为枯黄单档，"变绿"交给枯黄强度 `grassYellowK` 在雪盖期退回 0（强度 0 ⇒ shader 直接露出原贴图绿）。这样强度归零时露出的就是**原贴图本身**，与春季逐像素一致。

## 七、昼夜：把晨昏线从背面转到正面

第一版昼夜做了，但用户说"看不到"。排查发现太阳方向 `(3,4,6)` **几乎正对相机（+Z）**，正面圆盘 `dot≈0.84` 全是白昼，晨昏线整个落在球背面；环境光 0.75 + 半球光 0.7 又把暗部提亮，城市灯火只在左下边沿零星露出。

修法：

- 太阳改**侧光** `(1, 0.45, 0.55)`，让晨昏线穿过正面圆盘；
- 环境光 0.75→0.42、半球光 0.7→0.45、太阳 2.2→2.4，拉开明暗；
- 新增一层贴地压暗壳（1.0025）：夜半球压深蓝 alpha 0.62、晨昏带透暖橙霞光；
- 城市灯火点数 3400→6500、亮度 1.35→2.6、闪烁加深。

这里有个工程习惯值得说：`SUN_DIR` 我定义了**一次**，供太阳光 / 夜面灯火 / 夜面压暗 / 海面高光四处共用——单一数据源，避免各层晨昏线对不齐。

## 八、大气光晕：为什么彻底放弃几何球

大气一开始我用几何球做，试了两种都翻车：

- **BackSide 大半径**（1.10 / 1.26）：整个圆盘泛蓝；
- **FrontSide 贴边**（1.018 / 1.055）：变成一圈细亮环。

两者看起来都像**玻璃罩**。

最后改成**面向相机的径向渐变 Sprite**：中心透明、贴地球轮廓处最亮、向外平滑淡出到 0 ⇒ 完全没有几何边界。再沿轮廓叠 34 个柔和大斑，让辉光不是完美圆环、有云絮般的不均匀感，最后用 `destination-in` 遮罩强制内圈透明、外圈归零，杜绝任何硬边。

> 这是这类"包裹效果"的通用经验：**凡是需要柔和不留边界的发光，径向渐变 Sprite 往往比几何体更靠谱**，因为它天生没有几何轮廓线。

## 九、龙卷风：程序化、间歇性、海陆两栖

龙卷风是需求"偶尔出现几个"驱动的，全部纯程序化、零外部资源：

- `LatheGeometry` 双层漏斗 + 螺旋云纹 `CanvasTexture` + 4 个球云帽 + 贴地尘埃环；
- 生命周期周期 38~60s，只在 0.58~0.90 相位可见（淡入/持续/淡出），三个相位错开；
- 沿陆地缓慢行进，撞海岸 / 极区转向，且**一边旋转一边移动**（整团公转 + 三层漏斗差速反向旋转 + UV 滚动）；
- 只改 `opacity / visible / position / quaternion`，**绝不缩放**（硬约束：动画过程零缩放）。

后来用户补了一句"海上也有龙卷风"，于是落点池改成按索引交替生成**陆龙卷**和**水龙卷**，移动约束也从"撞海岸就转向"改成"**按自身环境判定**"——水龙卷只在海面走、陆龙卷只在陆地走。水龙卷的漏斗和水花环只改 `material.color` 偏冷蓝，**依然零缩放**。

还有一个落点细节：龙卷风要**额外避开森林簇**（树点 1/4 抽样 + 0.14 rad 约束），让灰白雾团落在开阔地，不与绿色树冠混成一团。

## 十、性能：三招把首屏从"光秃秃转很久"救回来

### 10.1 预烘焙纹理

程序化纹理是最耗时的一块（1024×512 实测生成 2.8s，首屏太慢）。我把五张纹理 + 一张 terrain 数据图用 `?bake=1` 一次性导出到 `docs/assets/tex/`，首屏直接 `TextureLoader` 载入，**任一文件缺失就整体回退到程序化生成**，页面照常可用。

`terrain.png` 是张数据图：R = 高程量化、G = 地表类别。回读后既恢复 `ELEV` 网格，又按类别精确重建 grass/forest 候选池 ⇒ **落点与程序化生成时逐点一致、可复现**。降分辨率到 768×384 后，生成时间从 2.8s 降到 0.4s。

### 10.2 渐进加载 + 分级并发

不能等所有 GLB 到齐再统一摆放——tree 的 GLB 有 3.4MB，慢时要几十秒，旧写法会让地球先光秃秃转很久。

改成"**落点先按固定顺序预分配 → 每个模型加载完立刻单独摆放**"，先到的小模型几秒内就出现。16 个 GLB 精简后合计约 5.58MB，按 tier 分级（主角 4 种 + 树为 tier0，其余 11 种 tier1）+ 并发上限加载。加载遮罩改成"**首帧 + 首个模型就绪**"才淡出，带真实百分比进度条；另有 4s 兜底强制隐藏，网络异常时不把用户挡在遮罩后面。

模型尺寸这里踩过一个著名的"**巨鹿**"bug：这些 GLB 的骨骼节点 bake 了 100×/140× 缩放，测量前若不先 `gltf.scene.updateMatrixWorld(true)`，`Box3` 会量到虚高 439.4 而不是真实的 4.3。**测量前必须刷新整棵世界矩阵。**

### 10.3 InstancedMesh 合批 + 自适应画质

- 169 个接触阴影贴片 + 150 棵树全部 `InstancedMesh` 合批，**一个 draw call**；走动的 19 只动物每帧只更新自己那一个实例矩阵，150 棵树是静态的、一次写入不再动。
- 按滚动 FPS 自适应画质（26 低 / 50 高，2.5s 窗口），`?quality=0|1|2` 可钉住便于校对。
- `window.__globeDebug.stats` 常驻输出 fps / draw calls / tris / geometries / textures / programs / quality，作为性能金标准。

## 十一、一个 CSP 兼容的深坑

严格 CSP 的预览环境常把 `blob:` 排除在 `connect-src` 之外。而 `GLTFLoader` 构造时会按 `typeof createImageBitmap` 选择 `ImageBitmapLoader`——一旦 `fetch(blob:)` 被拦，**贴图全丢、模型变纯白剪影**。

最省事的修法是全局 `window.createImageBitmap = undefined`，但那是"永久全局副作用"：整个页面生命周期都关掉了浏览器最快的纹理解码路径。

最终方案分三步：

1. **一次性探测** `blob:` 是否真被拦（造一个 blob URL 去 fetch，900ms 超时视为被拦）；
2. **仅在被拦时**临时禁用 `createImageBitmap`；
3. **全部 GLB 加载完立刻恢复原值**，另有 45s 兜底。

正常环境零改动。这个思路可以推广：**凡是需要改全局 API 来兼容的场景，先探测、按需临时改、用完立刻还原**，别留副作用。

## 十二、可复现性：为什么到处都是「独立 LCG」

我给整个系统加了一条硬约束：**落点必须可复现**。全局 `rand` 是固定种子的 LCG（`20261107`），但星星、光点、极光、流星这些纯装饰元素**绝不能消耗全局 rand**——否则它们每帧的随机调用会扰动后续的落点采样。

所以星空 / 城市灯火 / 龙卷风 / 月亮环形山各自用**独立的 LCG 种子**（9137 / 5521 / 7717 / 3319），流星甚至刻意用 `Math.random()`。这样装饰效果随便动，**169 个原有实例的落点一个都不变**。

> 这是程序化生成里非常值得养成的习惯：**把"影响布局的随机"和"纯装饰的随机"隔离到不同随机源**，否则调一个视觉参数，整个场景布局就悄悄变了，你都不知道哪里不对。

## 十三、把可调参数全部收敛到一处

早期参数散落在页面各处，调一次要全局搜。后来全部收敛到模块顶部的 `CONFIG` 对象（纹理尺寸、相机、行走速度、森林簇、数量、画质阈值、季节周期、山体幅度……），页面内各处只留**热路径短别名**，值全部来自 CONFIG，`window.__globeConfig` 暴露给 `?debug=1` 校对。

配套还留了一套调试钩子 `window.__globeDebug`：`stats`（性能）、`season`（四季各通道数值）、`moon.ndc/onScreen`（月亮可见性）、`mountains`（山体参数）、`tornadoTrace`（龙卷风海陆与位移）。**这些"金标准"让我在调"看不见的东西"（比如月亮到底入画没有、冬天强度是不是 0）时有数据可依，而不是靠截图猜。**

## 写在最后

这个文件从 v1 到 v6.5 全程只花了一天多，但每一版都是真实反馈驱动的返工。回头看，**真正花时间的不是"画一个地球"，而是那十几个"看起来对、跑起来不对"的瞬间**：

- 平底模型站在球面上会悬空；
- `SkeletonUtils.clone` 不克隆骨架引用，动画会串台；
- morph target 要存绝对位置，否则模型周期性长大缩小；
- `Float32BufferAttribute` 是复制不是引用，改了没反应；
- 材质名是复数 `Leaves`，正则 `/leaf/` 一个都匹配不到；
- 乘法染色永远染不出冷蓝灰，得换 shader 换色相；
- 积雪要用 over 合成而不是二选一，否则"先黄变绿再变白"；
- 大气用几何球一定留硬边，得用径向渐变 Sprite。

这些坑没有一个是"高级技巧"，全是对**底层机制理解不到位**留下的隐患。我把它们连同定位过程都写进了源文件的注释里（那个 300 行的变更记录就是我的踩坑日记），也整理成这篇文章——希望下一个人做类似东西时，能少撞几次墙。

如果你也想做一颗"活着"的星球，我的建议是：**先把它拆成一层层壳，再逐层往里加细节，并且从第一天就固定随机种子、留好调试钩子**。剩下的，就是跟一个个具体的 bug 短兵相接了。
