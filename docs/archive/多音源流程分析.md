## 关键证据及证据分析

### 审计结论（r5）

**总体判断**：架构方向正确、主链路没有致命故障，但“跨源兜底”和“同源去重”的边界处理不完整，存在 2 个应优先修的中高问题（取链最坏时延、跨源替换不校验标题），以及 4 个中/低问题。

整体架构成立：9 类源 + 统一 `NetworkMusicService` 契约 + `SourceVisibility` 门控 + `SearchAggregator` 并行聚合 + `NetworkMusicManager` 精确路由/跨源降级。**未发现“源关掉还能播/还能搜”的主链路逃逸**（采集期 + 结果期双重过滤、注销即清缓存）。但存在 6 处实质不正确或与自身语义冲突的实现：

1. **聚合结果重复**（中）：`SearchAggregator.kt:255-275` 网络分支经 `NetworkMusicManager.search()`（`NetworkMusicManager.kt:156-171` 会 fallback 到百度/Jamendo）取回别源歌曲并标成 `NETWORK_MUSIC`；百度/Jamendo 自己的分支同时返回同一批歌，而 `deduplicateWithinSource`（`SearchAggregator.kt:460-471`）只在**同源标签内**去重 ⇒ 同一首歌以两个标签重复出现，且同一关键词被请求两次。
2. **跨源替换可能播错歌**（中高）：`NetworkMusicManager.kt:519-535` 对候选只做“可播”校验，未做标题/歌手相关性判定（同源 `CandidatePicker` 有 `titleMatches`），自动替换可能播放无关结果。
3. **本地开关与“已下载恒可见”自相矛盾**（中）：`SourceVisibility.kt:40-44` 声明关闭本地=只显示已下载，但 `SearchAggregator.kt:353` 在分支入口就用 `localMusicEnabled()` 短路；`LocalMusicRepository.search()`（`:168-171`）返回含 `storageType=DOWNLOAD` 的全部索引 ⇒ 关闭本地后已下载歌曲从搜索整体消失。
4. **默认源修复口径不统一**（低中）：`NetworkMusicManager.defaultSource`（`:136-141`）会修复失效 key，但 `orderedServices()`（`:445-450`）仍用原始 `defaultSourceProvider()` ⇒ 搜索 fallback 顺序退化为 `ConcurrentHashMap` 迭代顺序，与 `getPlaylist/findArtist` 使用的修复值不一致。
5. **取链请求量与时延上限过大**（中）：`MetingApiService.resolvePlayUrlDetailed`（`:480-547`）对最多 4 端点 × 4 档位串行请求，每次 connect/read 15s（`:98-121`），叠加重定向跟跳+探活；搜索侧 `NETWORK_TIMEOUT=8s`（`SearchAggregator.kt:98`）会先丢弃结果（孤儿请求继续），下载侧无总超时。
6. **电台可下载判定错误**（低）：`DownloadKeys.kt:91-102` 只排除 `networkSource == "weather"`，RadioBrowser 歌曲 `networkSource == "radio"`（`RadioStation.kt:40`）被判为可下载，实际无对应源可取链。

### 本轮修复（r6/r7，提交 39a2bfa）

1. **跨源替换相关性闸门**：`NetworkMusicManager.resolvePlayUrlWithCrossSourceFallback` 先按 `CandidatePicker.titleMatches` 过滤标题，再按“同歌手优先”排序，仅对相关候选做可播校验；不再直接取首个可播搜索结果。
2. **取链总预算**：`MetingApiService.resolvePlayUrlDetailed` 引入 12s 总预算 + 600ms 最小发起阈值；`fetchPlayUrl` 改为按**绝对 deadline** 为每一跳设置 OkHttp 调用超时，最坏时延被封顶。
3. **网络分支跨标签重复**：`SearchAggregator` 网络分支只保留 `networkSource == meting` 的结果；百度/Jamendo 由各自分支提供，避免同一首歌双标签出现与重复请求。
4. **本地关闭仍显示已下载**：本地分支改为“恒进、按 `localMusicEnabled()` 收敛范围”，关闭时只保留 `storageType=DOWNLOAD` 并标为 DOWNLOAD 分支，结果层原有 `visible(it.source) && visible(it.song)` 过滤保持不变。
5. **默认源顺序确定化**：`orderedServices()` 改用修复后的 `defaultSource`，其余按 `Meting → 百度 → Jamendo → 字典序` 排序。
6. **电台不可下载**：`isDownloadableSong` 排除 `radio` 与 `weather` 两个流媒体源。
7. **注销期间缓存回写护栏**：解析完成后校验 `services[src] === svc`，源已被注销则不写直链/DEAD 缓存。
8. **去重键空白折叠**：`dedupeKey` 由“删除空白”改为“折叠为单空格”，避免 `A B` 与 `AB` 误判同曲。
9. **本地分支超时口径**：`withTimeoutOrNull` 改为与其他源一致的 `withHardTimeout`。

测试：更新 `NetworkMusicManagerTest`（候选标题改为同曲、新增“标题不匹配不替换”用例），新增 `DownloadKeysTest`（电台/天气电台不可下载、去重键空白语义）。

### 已修复的次要项
- 注销期间在途解析回写缓存：已加 `services[src] === svc` 护栏。
- 本地分支超时口径：已改为 `withHardTimeout`。
- `dedupeKey` 空白语义：已改为折叠单空格。

### 保留的设计限制（未改，需产品/数据侧决策）
- `RankedSong.matchScore` 恒为 80（`SourceIdentifier.kt:77`）⇒ 排序实际只按源优先级，跨源相关度未参与。改它需要一套相关度打分规则，且会影响全局排序，本轮不动。
- 历史歌曲 `networkPlatform` 为空时回退**当前**平台（`MetingApiService.kt:500`），换平台后播旧数据可能取到同 id 的异歌；属既有兼容行为，新数据已写快照（`:751`）。无历史平台信息可依，强行改写风险更大。
