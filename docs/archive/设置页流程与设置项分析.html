流程判定

“可见性判开关、注册表判能不能用、结果层再兜底”三段式是成立的：搜索聚合器、浏览合并、收藏/历史、封面解析都对 SourceVisibility 有显式调用；播放取链不 fallback 到别的源，失败后交给跨源替换。没有发现“关源后仍从该源产生新条目”的可见泄漏。

不成立的是“开关状态 = 生效状态”这一层：百度开关显示的是 enabled，生效要求“启用且已登录”； 下载总开关关闭时入口仍在；音质档位与设备能力不一致。这些是状态表达问题，不是门控结构问题。

三、不合理的设置项（对应问题 2）

编号设置项问题证据建议
P0-1通用 → 动画效果 开关只写偏好，全仓没有任何读取点；关掉后界面动画照旧。 GeneralSettingsSection.kt:103；AppSettings.kt:36；AppPreferences.kt:972,2352 要么接入统一动画时长/开关（Compose tween 统一入口），要么删除该开关，避免“假开关”。
P0-2缓存 → 歌词缓存 开关不影响缓存行为：LyricsManager 恒读/写持久缓存。 CacheSettingsSection.kt:85；LyricsManager.kt:59,176 在缓存读写前判 cacheLyrics，或把文案改成“仅控制新歌词写入”，并说明已有缓存需手动清理。
P0-3缓存 → 封面缓存 开关不影响缓存行为：Coil diskCache 恒启用，100MB 上限写死。 CacheSettingsSection.kt:86；NasMusicApp.kt:888-895 按开关重建 ImageLoader（或设置 diskCache(null)），否则删除开关。
P1-1音乐来源 → 百度网盘开关 checked = baiduEnabled，但真正生效 = 启用 且 已登录；未登录时开关显示“开”，搜索却完全没有百度结果，开关在说谎。 SourcesSettingsSection.kt:239；SourceVisibility.kt:73；NasMusicApp.kt:836-844 开关状态改用 isActive，或在行描述中显式显示“未登录，不参与搜索”，并把登录按钮放在同一视觉组。
P1-2下载 → 下载总开关 关闭后歌曲列表的 ⬇ 仍然渲染；点击 downloadSong 直接 return，没有任何提示，用户会判定“按钮坏了”。 UnifiedSongRow.kt:222-244；DownloadViewModel.kt:135 总开关关闭时隐藏/置灰 ⬇，点击给一次性提示“下载已关闭，请到 设置 → 下载 开启”。
P1-3播放 → 音质档位（无损） 所有设备都能选“无损”；不支持 FLAC 的设备在下游被静默钳到 320kbps，设置页仍显示“▶ 无损”，状态与事实不符。 PlayerSettingsSection.kt:185-196；NasMusicApp.kt:431-435；QualityTiers.kt:57 按 DeviceAudioCaps 过滤档位，或在“无损”行标注“本机将降级为 320kbps”；不要把钳制只放在播放时。
P1-4搜索空态文案 “未启用任何音乐源”只统计 Meting / 百度 / Jamendo；NAS 或本地开着但搜索无结果时也会显示这句，属于误报。 MainViewModel.kt:1536-1547；SearchTab.kt:156-166 文案改为“网络音乐源未启用”，或把 NAS / 本地纳入判据；更准确的说法是“当前参与搜索的源没有结果”。
P1-5智能电台（非设置页，但受开关影响） 采集侧只对 NAS 开关短路；本地库与 Meting 歌单采样无条件读取/请求，关源后仍会产生网络请求与磁盘读取，只是结果层再把歌滤掉。 SmartRadioManager.kt:292-334,340-357；MainViewModel.kt:3719-3726 把 localMusicEnabled / metingEnabled 作为 provider 注入 SmartRadioManager，采集侧直接短路；或给电台单独的三源开关。
P2-1下载 → 自动下载上限 “播放时自动下载”关闭时，上限数字仍可加/减；用户会以为改了有效。 DownloadSettingsSection.kt:87-103 上限行跟随自动下载开关置灰，或在描述中明确“仅自动下载生效”。
P2-2音乐来源 → 歌单与艺人数据源 候选只列 providesCatalog 的源（当前仅 Meting）；当默认源被“自愈”切到百度/Jamendo 时，卡内没有任何“当前默认”标记，用户看不到也无法改回。 SourcesSettingsSection.kt:460-492；SettingsScreen.kt:748-751；NasMusicApp.kt:848-864 始终渲染“当前默认源”一行（即便不在候选里），并解释“该源不提供歌单/艺人目录，仅作为搜索 fallback 起点”。
P2-3缓存 → 6 个清理入口 “封面缓存 / 提取封面缓存 / 封面地址表”三个入口都与封面有关，用户无法对应上方 19 条占用，也不知道该点哪个。 CacheSettingsSection.kt:114-178；CacheInventory.kt 按 CacheGroup 分组呈现清理按钮，或每个按钮显示“将释放 xxMB”；三个封面入口合并成一个带子选项的入口。
P2-4音乐来源 → 百度索引 → 重建索引 按钮不受百度开关门控；百度关闭时仍可发起全盘扫描（网络请求 + 写索引）。 SourcesSettingsSection.kt:366-371；NetworkMusicViewModel.kt:777-812 关闭时置灰并给理由“先启用百度网盘”，或允许“仅建索引不参与搜索”并明确说明。

四、位置不合理的设置项（对应问题 3）

这一节是信息架构建议，不是功能缺陷。判定标准：同一功能的“开关/配置/效果”是否在同一分区内可发现。

编号设置项当前位置为什么不合理建议位置
P-01音质档位（仅 Meting 生效）播放 → 音质卡 它只影响 Meting 取链，而 Meting 的开关、端点、当前平台分别在“音乐来源”和“网络高级设置”；用户在播放页改音质，却看不到它依赖哪个源。 音乐来源 → Meting 卡内（或保留在播放页但加“仅对 Meting 生效”的跳转链接）。
P-02歌词网络端点（酷狗 / 网易云）网络高级设置 → 歌词端点卡 “歌词显示 / 字号 / 高亮”在“歌词与 K 歌”，端点却在另一个分区；同一功能的配置被拆成两处。 歌词与 K 歌 → 新增“网络歌词来源”卡，或在歌词显示卡内放入口。
P-03网络测试网络高级设置 → 连通性卡（第一张） 它是排障动作，不是网络配置；放在端点配置最上方会让日常配置被诊断入口抢占注意力。 运行日志 → 诊断卡（与日志、版本信息同域）。
P-04天气 API Key / 腾讯位置 Key网络高级设置 → 天气 API Key 卡 服务对象是“天气电台”，不是网络音乐；与 Meting/MV/歌词端点混在同一分区，语义不同。 天气电台入口旁，或独立“外部服务”卡（放在数据/关于之前均可）。
P-05导出到外接设备 / 播放统计导出在“下载”，统计在“数据” 导出是数据搬运，与备份/歌单导入同域；播放统计是分析，不是数据管理。两者都借用了相邻分区的容器。 导出并入“数据 → 备份与恢复”；播放统计独立成卡或移入“关于”。
P-06焦点高亮通用 → 外观与动效 它解决的是“遥控器看不见焦点”，属于无障碍/输入设备，不是视觉风格。 可保留（改动成本低），但更合适的是“通用 → 遥控器与无障碍”独立卡。

五、空悬的设置项（对应问题 4）

判定口径

对 AppSettings 的 43 个字段逐个做全仓引用统计，排除 AppSettings.kt（定义）、 AppPreferences.kt（读写/备份）与设置页 UI 后，仍无任何引用 ⇒ 判定为空悬。 三个 P0 项都满足这个条件，不是“消费方藏在别处”的误判。

编号设置项存储键全仓消费方结论
D-01动画效果settings_animations 无。只有 AppSettings 定义、AppPreferences 读写和设置行本身。 删除或接入统一动画控制。
D-02歌词缓存settings_cache_lyrics 无。LyricsManager 直接 LyricsPersistentCache.get()，不读开关。 在 getLyrics / saveNetworkLyricsToCache 前判开关。
D-03封面缓存settings_cache_cover 无。Coil ImageLoader 的 diskCache 恒启用。 按开关构建 ImageLoader，或删除开关。

代码级“悬空接线”（不面向用户，但同样应清理）

  • SettingsScreen.kt:236 的 onRefreshModelStatus：SettingsBranch 传了 viewModel.downloadVM.refreshModelStatus()（SettingsBranch.kt:407），但 SettingsScreen 内部从未调用。 模型状态实际由进入设置页时的 LaunchedEffect 刷新，参数是死接线。
  • SettingsScreen.kt:287 的 baiduConnecting：传了但未消费；百度连接态由 baiduConnectionState 单独表达。
  • AppSettings.darkTheme：仅用于旧备份兼容（AppPreferences.kt:970,2349）， 设置页不再暴露。这是刻意的迁移字段，不算缺陷，但不应再被当成“主题开关”。

看起来像空悬、但实际不是的四项

  • NAS 开关在未连接时“开了也没内容”：开关只决定参不参与搜索/浏览，连接状态由后端注册表决定。 卡片里已显示“未连接，去配置”状态，语义是分开的（SourceVisibility.kt 的边界说明）。
  • Jamendo 开关显示“关”但底层 jamendoEnabled=true：开关显示的是“生效 = 开关且 Client ID 非空”， 未配 ID 时点开会先弹编辑框（SourcesSettingsSection.kt:410-429），这是刻意的两条件表达。
  • 本地开关关闭后已下载歌曲仍可见：这是设计（SourceVisibility 的 DOWNLOAD 分支恒可见）， 不是门控遗漏。
  • 下载位置选“外接”但实际写内置：外置卷不可用时回落并在设置页提示（DownloadSettingsSection.kt:118-133）， 不是假开关。

逐源结论

NAS —— 全部链路正确

搜索分支实时读 nasMusicEnabled()（SearchAggregator.kt:215）；浏览/合并、收藏、年份/流派/歌单、 封面与艺人封面输入都按可见性置空（MainViewModel.kt:1844-2323,2685-2898）； 电台采集侧直接不发 NAS 请求（SmartRadioManager.kt:292-334）。 关源会清流派/年份/歌单/收藏/随机歌，重开按源重拉（MainViewModel.kt:918-950）。 唯一注意：首页统计数字不随开关变化（设计上统计的是“库里有这么多”，不是“当前列出多少”），缺少一句说明。

本地曲库 —— 搜索/浏览/收藏正确，电台采集未短路

搜索分支恒进，但关闭时只保留 storageType=DOWNLOAD 并改标 DOWNLOAD（SearchAggregator.kt:359-410）， 与“关 = 只显示已下载”一致；浏览用 visibleLocalSongsNow()；收藏由 networkFavorites 过滤。 问题：SmartRadioManager 的 localSongsProvider 无条件读缓存（SmartRadioManager.kt:330）， 关本地后仍会读取本地库；结果层虽过滤（MainViewModel.kt:3719-3726），但不是“关了就停”。

百度网盘 —— 门控正确，开关语义不正确

搜索分支判 sourceVisibility.isVisible(BAIDU_PAN)（SearchAggregator.kt:300）； 浏览/合并、封面输入按 baiduVisible 置空；播放取链靠 service 注销失败； 收藏/历史按 SourceVisibility 过滤；重开由 refreshBaiduConnectionState → onMergedDataInvalidated 重新填入索引（NetworkMusicViewModel.kt:303-330），不存在“重开空白”。 问题：UI 开关绑 baiduEnabled，真正生效还要求已登录；未登录时开关与结果不一致（P1-1）。 索引重建也不受开关门控（P2-4）。

Meting —— 搜索/取链/目录正确，电台采集未短路

关源即 unregisterService（MainViewModel.kt:866-870）：搜索分支判可见性（SearchAggregator.kt:270）， 播放取链因 services[src] 为空失败（NetworkMusicManager.kt:300-330）， 歌单/艺人无 service 返回空（NetworkMusicManager.kt:250-266）。 重开 registerService + loadRandomSongs()。 问题：电台仍会请求 Meting 歌单采样（SmartRadioManager.kt:340-357），只是结果被过滤（P1-5）。

Jamendo —— 开关与 Client ID 双条件正确

注册条件 = 开关且 ID 非空（NasMusicApp.kt:584-586,837-844）；可见性同一判据（SourceVisibility.kt:74）； 搜索、Jamendo 页、播放取链都随之生效；未配 ID 时点开关会先弹 ID 编辑框而不是“翻开但静默不生效”。 它不提供歌单/艺人目录（实现返回空），因此默认源候选不列它是正确的。

洛雪 —— 作为“通道”的开关正确

它不是源：搜索不受影响；总开关关闭时 refreshLxRuntime 清空 lxHostPool， 增强器逐次返回 null、退回原 302 链路（NasMusicApp.kt:872-878）； 切换总开关会清直链缓存（MainViewModel.kt:1101-1107）；Meting 关闭时子块置灰且开关不可点（LxScriptsSubBlock.kt:132-141）。

一句话结论

结构对、主链路对、逐源门控基本对；错在“开关的承诺”——3 个开关完全没接线， 3 处开关显示的状态不是真正生效的状态，下载/音质/搜索空态会让用户误判“功能坏了”。 先修 P0 与 P1，成本不高，收益是“用户不再怀疑开关”。
